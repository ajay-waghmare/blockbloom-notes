**Verdict on progression:** the week was well executed — release discipline (notes per versionCode, upload
→ internal → staged production, read-backs on the listings), the revenue groundwork, and the in-app update

Everything below is ordered by that.

## 2. The 11–19 Oct code, reviewed

What is good: `InAppUpdateHost` is a clean seam with a no-op for tests and a Play Store fallback; the
out-of-coins flow replaces a dead end (greyed buttons) with two real exits; `placementSquashStretch` is a
pure function, honours reduce-motion, and has a real test; all 27 new strings exist in all seven locales;
the economy still routes every movement through `Wallet`. Findings, most important first:

1. **"Watch Video (+1 Free)" can be a dead end.** `OutOfCoinsPrompt.canWatchAd = BuildConfig.ADS_ENABLED`
   (GameViewModel), but the game-over dialog gates its ad buttons on `state.adsActive` (SDK initialised +
   consent resolved). A player who declined consent, or taps before the SDK is up, gets the button, then
   "No ad available". Fix: `canWatchAd = _state.value.adsActive`. One line.
2. **The lifeline bundles are priced worse than converting coins, so nobody should buy them.** 10 gems →
   500 coins → 6.7 Hammers (75 each) / 8.3 Shuffles (60). The "5 Hammers for 15 gems" bundle is worth 375
   coins where 15 gems buys 750; "5 Shuffles / 12 gems" = 300 coins vs 600; the Mega pack = 525 coins vs
   1,000. Either price bundles below the coin route (the normal pattern: bundles are the discount) or make
   them carry something coins cannot buy. As shipped, three of the five cards are decoys.
3. **Gem→coin exchange is mislabelled in the ledger and inflates a stat.** `exchangeGemsForCoins` debits
   gems as `LIFELINE_BUY` and credits coins as `IAP_PURCHASE`; `Wallet.earn(COINS)` also bumps
   `totalCoinsEarned`, so the Stats screen's "Coins earned" and the `coins_5000` achievement (pays 3 gems)
   now count converted gems. Add `TxReason.GEM_EXCHANGE` and a `Wallet.convert` that does not touch the
   earned total. The ledger is the audit trail the design doc says a server will reconcile against.
4. **"Need more gems! Get gem packs below." is untrue today.** No products exist in Play yet, so the Gems
   section is hidden and the toast points at nothing. Until the catalog is live, say where gems do come
   from (daily challenge, levels, achievements) or hide the bundle cards behind `state.gemPacks.isNotEmpty()`.
5. **Near-miss framing fires on bad runs.** `diffToBest in 1..150` with `best >= 100`: a 10-point run
   against a best of 120 shows "SO CLOSE! Only 110 pts from your best". Make the absolute window scale,
   e.g. `diff <= max(30, best * 0.12)`, and keep the 88% rule. Praising a bad run reads as fake.
6. **Two of the three new test classes do not test production code.** `MonetizationEconomyTest` asserts
   on local variables and data-class fields (the exchange logic in the view model is never called);
   `InAppUpdateHostTest` tests a fake defined inside the test. `PlacementJuiceTest` is the real one. The
   exchange functions belong in a small `Economy` class the test can call, which is also finding 3's fix.
7. **GameViewModel is now ~1,800 lines** and the monetisation functions, the update check and the prompt
   state all went into it. The split that was "when the next feature lands" is now overdue: `Economy`
   (exchanges, out-of-coins, free lifeline), `Updates` (in-app update + the Remote Config gate), leaving
   the board/run logic. Mechanical, no behaviour change, and it makes findings 3 and 6 testable.
8. **Debug builds report to the same analytics property.** `google-services.json` registers
   `com.aweagle.blockbloom.debug`, so every emulator session on either laptop (`sdk_gphone*`,
   the OnePlus8Pro reinstalls) lands in GA4 as new users. Cleanest fix: `buildTypes.debug {
   buildConfigField("boolean", "ANALYTICS_ENABLED", "false") }`. The numbers above are slightly inflated by it.
9. **Commits from the new laptop are authored as `swati waghmare <swati.waghmare2905@gmail.com>`** (all
   ten since 11 Oct). Harmless for a solo project, but GitHub attribution and the Play/AdMob paper trail
   name someone else; `git config user.name/user.email` on that machine if unintended.
10. Smaller: `exchanged_gems_for_coins` uses `%d` instead of `%1$d` (lint); the free-lifeline path for
    REVIVE grants an inventory item and closes the prompt, so the player must tap Continue a second time,
    while the same dialog already offers an ad-revive button when ads are active (two routes, one with an
    extra tap); no analytics event when the update banner is shown or tapped, so the migration from 1.10.0
    cannot be measured except by version share.

Not verifiable from here: whether the Play **Data Safety** form and the "Contains ads" declaration were
updated when ads went live (the manifest has carried `AD_ID` since June; the journal records listings,
privacy policy and app-ads.txt, not the form). Worth a look in the console: that is the one policy item
that can suspend a listing.

## 3. What I would do, in order

1. **Attack the first session, not the shop** (biggest lever, 2–3 days). Half of installs leave; 47%
   never clear a line. Put a near-full row on the first board so the first placement clears (the
   "place-before-onboarding" item deferred in June), log `first_clear` timing, and read D1/D7 from the GA4
   retention report before and after. Nothing else moves the revenue ceiling as much as keeping players.
2. **Ship a vc24 hygiene release with findings 1, 3, 4, 5, 8** (half a day of code, all small, all
   low-risk) once the Play product catalog is live, so the gems section and the toast become true in the
   same build.
3. **Fix the bundle maths before anyone sees them with gems in hand** (finding 2): a pricing table in
   one place (`ShopCatalog`) instead of five literals in `ShopScreen`, with a unit test that every bundle
   beats the coin route.
4. **Split the view model** (finding 7) as the first commit of the next feature branch, before more code
   goes in. Half a day, mechanical.
5. **Measure before touching the ad dials.** Rewarded-only is the right default; the dials exist so the
   banner and interstitial can be tested on a slice, not guessed. Read AdMob eCPM/fill for two weeks first.
6. **Housekeeping on this laptop:** `main` is four release branches behind and carries an uncommitted
   `play-rollout.js` plus an untracked `tools/release-notes/vc21.json` that is wrong; discard both, then
   merge `release/2026-10-17` into `main` (vc23 is in production, which is the documented point to merge).
   Ajay's merge, per the standing rule.

**Alternatives considered:** a full rewrite of the shop into a Play-driven catalog (overkill until products
exist); switching the interstitial on for revenue now (would trade the one thing the listing can still
claim — "relaxing" — for cents a day at this DAU); building Arrow Bloom first (the first-session fix here
is cheaper and compounds across both games once the engine is shared).

**Effort:** items 1–4 together are about a week of evenings; item 2 alone is the quickest win.
**Long-term:** retention first, then catalog-driven pricing, then shared engine for Arrow Bloom.
